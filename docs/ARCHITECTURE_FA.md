# معماری App-Time

## هدف

App-Time یک برنامه اندرویدی فارسی برای مدیریت نوبت، مشتری، پرسنل، پیامک، مالی و گزارش‌های کسب‌وکار است. معماری پروژه از ابتدا طوری نگه داشته می‌شود که نسخه‌های جدید بتوانند روی نسخه قبلی نصب شوند و داده‌ها/تنظیمات کاربر در آینده با Migration مناسب حفظ شوند.

## اصول ثابت انتشار

1. `applicationId` برنامه ثابت می‌ماند.
2. `versionCode` در هر انتشار افزایش پیدا می‌کند.
3. تمام نسخه‌های عمومی باید با **همان کلید امضای اصلی** امضا شوند.
4. فایل خصوصی امضا داخل GitHub عمومی قرار نمی‌گیرد.
5. تغییرات دیتابیس آینده باید Migration داشته باشند و حذف خودکار داده مجاز نیست.
6. UI اصلی فارسی و RTL است.
7. منوی همبرگری در سمت راست Top Bar همیشه در دسترس است.
8. دکمه Back در صفحات داخلی باید ابتدا به صفحه قبلی برگردد و فقط از ریشه برنامه اجازه خروج بدهد.
9. تمام فایل‌های سورس باید کامنت توضیحی داشته باشند تا نقش هر بخش برای توسعه‌دهنده مشخص باشد.

## نسخه 1.1.0

### لایه UI

در نسخه فعلی `MainActivity.kt` نقش UI Shell را دارد و شامل موارد زیر است:

- Theme و رنگ‌بندی
- مدل مقصدهای ناوبری
- Back Stack داخلی Compose
- Drawer راست‌چین
- داشبورد
- مشتریان
- نوبت‌ها
- پیامک
- پرسنل
- حسابداری
- گزارش‌ها
- تنظیمات
- صفحات اطلاعاتی

### ناوبری

به‌جای تغییر مستقیم یک متغیر Screen، یک `mutableStateListOf<Screen>` به‌عنوان Back Stack نگهداری می‌شود. هر صفحه جدید به Stack اضافه می‌شود و Back فقط آخرین مقصد را حذف می‌کند. در نتیجه دکمه Back اندروید در صفحات داخلی Activity را نمی‌بندد.

### نسخه و بروزرسانی

ورژن قابل نمایش از `BuildConfig.VERSION_NAME` خوانده می‌شود تا متن Drawer، درباره نرم‌افزار و صفحه بروزرسانی با Gradle همگام باشد. `version.json` برای اتصال سیستم بررسی بروزرسانی آینده نگهداری می‌شود.

### امضای Release

`app/build.gradle.kts` فقط وقتی فایل `signing/keystore.properties` وجود داشته باشد SigningConfig خصوصی را فعال می‌کند. این پوشه در `.gitignore` است و فقط داخل نسخه خصوصی سورس مالک پروژه نگهداری می‌شود.

## معماری پیشنهادی نسخه‌های بعد

برای جلوگیری از بزرگ شدن `MainActivity.kt`، در توسعه بعدی کد به ساختار زیر منتقل شود:

- `ui/` برای Screen و Componentهای Compose
- `navigation/` برای Route و NavHost
- `data/local/` برای Room
- `data/remote/` برای API
- `data/repository/` برای Repositoryها
- `domain/` برای Model و UseCase
- `service/` برای اعلان، پیامک و Sync
- `worker/` برای یادآوری‌های پس‌زمینه

## قواعد داده

- هیچ Update نباید داده کاربر را بدون درخواست صریح حذف کند.
- Backup باید قبل از عملیات Migration پرریسک قابل تهیه باشد.
- اطلاعات احراز هویت و Tokenها باید در Storage امن نگهداری شوند.
- رمزها، API Keyها و Keystore هرگز داخل GitHub عمومی Commit نشوند.
